## Z1 — Forged/mutated proof → verify false / revert

**Attack description:**
> A forged or mutated proof (a proof NOT generated by the prover using
> the actual witness + proving key) must be rejected by the verifier —
> either via the on-chain Groth16 verifier returning false, or via the
> Solidity contract reverting with `ComplementarityProofFailed` /
> `TravelRuleProofInvalid`.

**Canon citation:** BTCP §5.6 Phase 2 verbatim (CANON_EXTRACT.md §1.2):
> "TRION searches for H_intent_B that is complement of H_intent_A. Both
> parties prove complementarity through ZK proof..."

**Test method:**
- Requires the prove/verify round-trip: generate a valid proof, mutate
  one byte (or apply an algebraic transformation), attempt verify, expect
  false.
- **Status: `[OPEN]` per Phase 3 BLOCKER** (Groth16 setup exceeds sandbox
  timeout per PHASE3_BENCHMARKS.md §4.2).

**Mathematical guarantee (documented honestly):**
- The R1CS constraints (MEASURED 2,686 for S1 Phase 2 — see
  `PHASE3_BENCHMARKS.md §2`) bind the proof to the witness. Soundness is
  a property of the Groth16 proving system, not the circuit. The
  verifier's pairing check:
  `e(A, B) = e(alpha, beta) · e(L_pub, gamma) · e(C, delta)`
  rejects any proof NOT generated by the prover using the actual witness
  + proving key. The `L_pub` term absorbs the public inputs into the
  verification equation, binding the proof to specific public inputs.
- On-chain enforcement (Phase 4): `ComplementarityVerifier.sol` enforces
  `PROOF_LEN_BYTES=256` + `PUBLIC_INPUTS_LEN=5` (Phase 1 MEASURED), then
  forwards the decoded `(A, B, C)` to the snarkjs-generated leaf
  verifier which performs the pairing check.

**Result:** `[OPEN]` per Phase 3 BLOCKER.

**Evidence:**
- `PHASE3_BENCHMARKS.md §4` — BLOCKER + `[OPEN]` status with threshold
  criteria for closure.
- `zk-circuits/zk_complementarity_proof/build/circuit.r1cs` — MEASURED
  2,686 constraints, 5 public inputs (the constraint structure).
- Test script: `zk-circuits/tests/z1_z4_soundness_battery.py`
  (documents the OPEN status + mathematical guarantee).

**Label per R-LABELS:** `OPEN`

## Z3 — Complementarity soundness: non-complement pair cannot produce proof

**Attack description:**
> Two intents A and B that are NOT complements (where `asset_in_A !=
> asset_out_B` OR `asset_out_A != asset_in_B`) must NOT be able to
> generate a valid complementarity proof. The circuit should refuse to
> produce a witness; the prover should fail at the witness-generation
> step.

**Canon citation:** BTCP §5.6 Phase 2 verbatim (CANON_EXTRACT.md §1.2):
> Verify: `asset_in_A == asset_out_B AND asset_out_A == asset_in_B AND
> magnitude_A ≈ magnitude_B`

**Test method:**
- Requires the prove/verify round-trip.
- Mathematical guarantee documented from the constraint structure: the
  circuit has hardcoded equality constraints
  `eqIn.out === 1` (asset_in_A == asset_out_B) and
  `eqOut.out === 1` (asset_out_A == asset_in_B).
- **Status: `[OPEN]` per Phase 3 BLOCKER** (round-trip required).

**Mathematical guarantee:**
- The circom template (`zk-circuits/zk_complementarity_proof/circuit.circom`
  lines 79-90) hardcodes:
  ```
  eqIn.in[0]  <== intentA[IDX_ASSET_IN]    (asset_in_A)
  eqIn.in[1]  <== intentB[IDX_ASSET_OUT]   (asset_out_B)
  eqIn.out    === 1                          (asset_in_A == asset_out_B)

  eqOut.in[0] <== intentA[IDX_ASSET_OUT]   (asset_out_A)
  eqOut.in[1] <== intentB[IDX_ASSET_IN]    (asset_in_B)
  eqOut.out   === 1                          (asset_out_A == asset_in_B)
  ```
- A non-complement pair CANNOT satisfy these constraints. The witness
  generator (snarkjs wc) returns "constraint is not satisfied:
  eqIn.out === 1" or similar. No valid witness ⇒ no proof is generated.
- The prove step (`snarkjs groth16 prove`) requires a satisfying
  witness; without one, it fails before producing a proof.

**Result:** `[OPEN]` (round-trip) + VERIFIED (constraint-level).

**Evidence:**
- Constraint-level evidence (verified in test script):
  ```
  Constraint lines present: True
  (eqIn.out === 1, eqOut.out === 1, ltAB.out === 1, ltBA.out === 1)
  ```
- Test script: `zk-circuits/tests/z1_z4_soundness_battery.py` (function
  `check_complementarity_soundness_constraints`).
- Round-trip blocker: `PHASE3_BENCHMARKS.md §4.2` (Groth16 setup > 240s).

**Label per R-LABELS:** `VERIFIED (constraint-level) + OPEN (round-trip)`

## Z5 — Sensing Oracle privacy (spec falsification per BTCP §13)

**Attack description:**
> Per BTCP §13 verbatim (CANON_EXTRACT.md §4.11): "TRION can reconstruct
> private behavior from `public_commitment` alone." This is THE spec's
> own falsification condition for the Sensing Oracle privacy property.

> `behavioral_hash = Hash_DNA(private_behavior || private_nonce)`,

**Canon citations:**
- BTCP §13 Falsifiability Table (CANON_EXTRACT.md §4.11).
- BTCP §7.1 Sensing Oracle Protocol (CANON_EXTRACT.md §4.1):
  `behavioral_hash = Hash_DNA(private_behavior || private_nonce)`,
  `public_commitment = Hash(behavioral_hash)` — hash of hash, no content.
- BTCP §7.1 (CANON_EXTRACT.md §4.3): "TRION stores: public_commitment
  ONLY — NOT the behavior."

**Test method:**
- Write a Python script
  (`zk-circuits/tests/z5_reconstruction_attempt.py`) that:
  1. Constructs a SYNTHETIC behavior space of 1,000 candidate behaviors.
  2. Picks one as the "true" private_behavior; computes
     `public_commitment` via the Phase 2 `hash_dna.py` helpers.
  3. Brute-force scans the 1,000 candidates × 32 candidate nonces
     (32,000 combinations total): for each candidate (behavior, nonce),
     checks whether
     `Hash(Hash_DNA(candidate_behavior, candidate_nonce)) ==
     public_commitment`.
  4. Confirms ZERO matches (the true behavior is outside the synthetic
     candidate set; even if it WERE inside, the true nonce would also
     have to be guessed — probabilistically negligible).
- Real-world search space: ~2^256 (SHA3-256 preimage) — astronomically
  larger than the SYNTHETIC-DEMO space.

**Result:** PASS (reconstruction fails — 0 matches across 32,000
combinations).

**Evidence:**
```

[Z5] SYNTHETIC search space: 32000 combinations

```
- Test script: `zk-circuits/tests/z5_reconstruction_attempt.py`.

**Cryptographic guarantee (documented honestly):**
- `public_commitment` is a hash-of-hash. SHA3-256 (and Poseidon, the
  in-circuit choice) are preimage-resistant (NIST FIPS 202; best-known
  attack ~2^256 brute force). Recovery is computationally infeasible.
- Hash_DNA dual-strand construction: even recovering `behavioral_hash`
  from the antisense strand requires SHA3-256 preimage (same
  difficulty).
- Simulator / HV-ZK argument: the ZK proof itself is computational
  zero-knowledge — a polynomial-time simulator (Goldreich-Micali-Wigderson
  / Blum-Feldman-Micali for Groth16) produces a proof distribution
  computationally indistinguishable from real proofs WITHOUT the witness.
  Therefore the public_commitment + ZK transcript together reveal
  NOTHING about private_behavior beyond what is implied by the public
  inputs.

**Label per R-LABELS:** `SYNTHETIC-DEMO` (small behavior space; real-world
space is astronomically larger per SHA3-256 preimage resistance).

**Spec falsification condition:** explicitly tested per BTCP §13. The
attack fails (reconstruction succeeds in 0 of 32,000 attempts); the
spec's privacy claim holds on the SYNTHETIC-DEMO surface. The real-world
guarantee is SHA3-256 preimage resistance + HV-ZK.

- Source file: `zk-circuits/zk_behavioral_credential/circuit.circom`.

**FINDING (documented honestly, not a redefinition):**
The S4 behavioral_credential circuit does NOT contain an explicit
`pattern_fields[0] >= threshold` (or equivalent) constraint. The
circuit's constraints are: (a) behavioral_hash Poseidon binding;
(b) pattern_commitment Poseidon binding; (c) credential Poseidon
binding; (d) range checks on `pattern_fields[i] ∈ [0, 2^32)`.

The SILENCE property (sub-threshold entity cannot obtain coherence-TRUE
proof) is therefore implemented at the **TRION-emission layer** (R-CHANNELS
surface), NOT at the circuit satisfiability layer:
- The ZK proof proves the pattern is correctly committed via
  behavioral_hash + pattern_commitment + credential.
- TRION reads the public pattern_fields (via the public_commitment)
  and computes the COHERENCE_SIGNAL (TRUE/FALSE) at the emission layer
  using its own threshold check.
- If coherence_score < threshold, TRION emits COHERENCE_SIGNAL=FALSE
  (this IS the silence — the protocol publishes FALSE, not the
  underlying behavioral content).

Per WP-Feb epigraph verbatim: "When any plane fails: silence. The
silence is information." The silence IS the FALSE emission — it carries
the information "this entity is below threshold" WITHOUT revealing what
behavior caused the failure (R-ABSENT).

A sub-threshold entity CAN technically generate a ZK proof (because
the circuit does NOT have a C >= threshold constraint), but TRION will
emit COHERENCE_SIGNAL=FALSE for that proof at the emission layer. The
SILENCE property is therefore preserved at the R-CHANNELS surface, not
at the circuit satisfiability surface.

**Label per R-LABELS:** `VERIFIED (constraint-level) + OPEN (round-trip)`

## Z12 — Malleability: proof re-encoding canonical or rejected

**Attack description:**
> A Groth16 proof is a unique algebraic representation of the witness.
> A malleability attack attempts to re-encode a valid proof into a
> different proof for the same public inputs (allowing replay /
> double-spend). The verifier must reject any re-encoded proof.

**Canon citation:** BTCP §5.6 Phase 2 verbatim (CANON_EXTRACT.md §1.2).

**Test method:**
- Requires the prove/verify round-trip.
- **Status: `[OPEN]` per Phase 3 BLOCKER** (Groth16 setup exceeds
  sandbox timeout per PHASE3_BENCHMARKS.md §4.2).

**Mathematical guarantee (documented honestly):**
- Groth16 proofs are non-malleable by construction. The verifier's
  pairing check:
  `e(A, B) = e(alpha, beta) · e(L_pub, gamma) · e(C, delta)`
  binds the proof to the witness + public inputs. Any malleability
  transformation producing a different `(A', B', C')` that satisfies
  the equation requires breaking the SDH / q-SDH assumption (discrete
  log in the source group of the pairing).
- The `L_pub` term absorbs the public inputs into the equation — a
  proof generated for public inputs X cannot be re-encoded to verify
  for different public inputs X' because the `L_pub` term would change,
  breaking the pairing.

**On-chain enforcement (Phase 4 contracts):**
- `ComplementarityVerifier.sol` enforces `PROOF_LEN_BYTES=256` +
  `PUBLIC_INPUTS_LEN=5` (Phase 1 MEASURED). The proof is decoded into
  `(A, B, C)` and forwarded to the circuit-specific `IGroth16Verifier`
  leaf (snarkjs-generated) which performs the pairing check.
- `IntentCommitmentRegistry.sol` tracks `IntentRevealed` state per
  `H_intent` pair. A second reveal with the same `H_intent_A` +
  `H_intent_B` reverts with `IntentAlreadyRevealed` — this is the
  application-layer replay protection (orthogonal to the ZK proof's
  cryptographic non-malleability).

**Result:** `[OPEN]` per Phase 3 BLOCKER.

**Evidence:**
```

  ComplementarityVerifier.PROOF_LEN_BYTES = 256
  ComplementarityVerifier.PUBLIC_INPUTS_LEN = 5
  ComplementarityVerifier decodes & forwards to leaf verifier: True
  IntentCommitmentRegistry.IntentAlreadyRevealed error: True
  IntentCommitmentRegistry isRevealed check: True

```
